# Testing the airv2 web app locally

## Hybrid store origins (main host /mini/... + mini host) local testing
- Simulate both hosts against one `next start :3999`: `MINIAPP_ORIGIN=http://localhost:3999` makes `localhost:3999` the mini host (middleware compares the Host header to `new URL(MINIAPP_ORIGIN).host`), while `127.0.0.1:3999` is the main host. Main-host routing table (middleware.ts): `/mini` → store home 200, `/mini/<slug>` → internal rewrite to `/mini/store/<slug>` (detail 200), `/mini/store/<slug>` → 308 `/mini/<slug>`, `/mini/<slug>?t=|?g=`, `/mini/login`, `/mini/publish`, `/mini/<slug>/app.js` → 308 to the mini origin.
- Gotcha: when MINIAPP_ORIGIN is a localhost URL, Next normalizes redirect `Location` headers to RELATIVE paths (e.g. `location: /login` instead of `http://localhost:3999/login`), which looks like a same-host redirect bug. To assert absolute mini-origin Locations, start a second server on another port with `MINIAPP_ORIGIN=https://mini.wzrd.tech` and curl its headers — with a non-localhost origin the 308s carry the full absolute URL.
- Canonical/OG/JSON-LD detail URLs come from `env.appOrigin()` (default `https://app.wzrd.tech`) via `canonicalDetailUrl()` in lib/miniapps/discovery.ts — leave APP_ORIGIN unset to test the default. Per-host links come from `storePaths()` (lib/miniapps/storePaths.ts, keyed on the middleware-owned `x-mini-host` header): main host cards → `/mini/<slug>`, Sign in/Publish → mini-origin `/login`/`/publish`, search form action `/mini`; mini host keeps `/store/<slug>`, `/login`, action `/`.

## Composio connect flow testing (connect mini-app + onboarding "Connect your Apps")
- Local prod server + real env exercises the real Composio backend: clicking Connect POSTs `action=connect` → `beginConnect` → 303 to `https://connect.composio.dev/link/lk_…`, which server-redirects straight to the provider's login (Airtable/Google/Notion reach real sign-in pages). Don't complete OAuth in tests; reaching the provider login proves the chain.
- Gotcha (root-caused 2026-08-28): `listToolkits()` uses `/toolkits?limit=100&managed_by=composio&sort_by=usage` and does NOT filter `no_auth:true` toolkits (composio, composio_search, codeinterpreter, browser_tool, hackernews, weathermap, text_to_pdf). Connect on those → Composio 400 `ToolRouterV2_ToolkitsIsNoAuth` → unhandled ComposioApiError → bare HTTP 500 page. Check catalog with `curl …/toolkits… | jq '[.items[]|select(.no_auth)|.slug]'`.
- Direct API probes with `COMPOSIO_API_KEY` (same key on prod, verify via Vercel env `?decrypt=true` hash-compare): GET `/tool_router/session/{id}`, POST `…/session`, POST `…/session/{id}/link {toolkit,callback_url}` all under `https://backend.composio.dev/api/v3.1` with `x-api-key`.
- Each Connect click upserts a `connections` row `status=pending` for that toolkit — clean test rows via PostgREST DELETE afterwards, or the UI shows "Resume" forever.
- Prod mini sessions are NOT mintable locally: prod MINIAPP_SIGNING_KEY and SESSION_SECRET differ from the local env file (token exchange logs `invalid token` 403), even though Supabase and COMPOSIO_API_KEY are shared.

## Hosted approval sheet (/approve/<decisionId>) + AgentMail calendar testing
- Approval deep links: sign `{use:"approval_link",userId,decisionId,exp}` HMAC-SHA256 with local `MINIAPP_SIGNING_KEY` (base64url payload.mac, `?k=`). Open on the MAIN host (`http://127.0.0.1:3999/approve/<id>?k=…`) — on `localhost:3999` (mini host) the client's `/api/approvals/<id>` fetch 404s via middleware and the sheet shows the expired-link error.
- Seed a testable payment approval with a `payment_requests` row (status pending, amount_cents, currency usd, expires_at future) + `decisions` row (kind payment_request, ref=request id, status pending). Decline flips both to dismissed; reopening the link renders the resolved state. With dummy Stripe keys Approve surfaces "could not resolve this approval — try again" and everything stays pending; `payment_requests.stripe_payment_intent_id` stays null on reloads (intent only minted by the Express lane, which needs a real publishable key).
- Expired/tampered `k` or unknown decision id → "This link has expired. Open the app and check Needs You." (no 500).
- Calendar mini-app (`/calendar?t=…`, app slug `calendar`): live AgentMail v1 calendar routes (free-busy, booking, rsvp) 404 — the page degrades gracefully (agenda intact, strip omitted, booking button re-rendered, server logs `… failed` JSON). One-tap Accept/Decline on invite decisions flips the `decisions` row even when the remote RSVP 404s. Deck swipe: `.frame[data-swipe-prev/next]`, synthetic TouchEvents on `.frame` navigate Agenda↔Timeline↔Month; inbox threads carry `data-swipe-prev=/inbox`.
- Onboarding slide slugs post-restructure: `welcome, environment (Computer), selfies (Photo Booth), imessage, onairos, connect, agent`; Get started is the default/fallback for unknown `?step=` values. The Connect Link (Stripe wallet) panel is `?step=link` inside the Connect your Apps stepper.

## Production acceptance testing (airv2.vercel.app / mini.wzrd.tech)
- No browser session is obtainable on prod: login is thirdweb SMS OTP (needs a real phone) and the prod SESSION_SECRET can't be read from Vercel (values come back encrypted), so a locally minted `air_session` cookie won't validate. Session-gated surfaces (media upload-url, publish icon, Apps tab) are untestable on prod without the user; test them locally instead.
- Deployment status/env inventory: Vercel API with `VERCEL_TOKEN` (`/v6/deployments?projectId=...&teamId=...&target=production`, `/v9/projects/:id/env`). Runtime logs are a live tail: `curl -sN /v1/projects/:id/deployments/:dpl/runtime-logs` in the background, then fire the request — invaluable for seeing facilitator/verify errors behind a bare 500.
- x402 on prod without funds: seed `x402_enabled=true, x402_price_usdc=<small>` on an owned published app via the service-role PostgREST (revert after). Anonymous GET with `Accept: application/json` → 402 JSON challenge; browser GET → HTML pay page. To prove the CDP facilitator lane: craft an exact-scheme X-PAYMENT (base64 JSON `{x402Version,scheme:"exact",network:"base",payload:{signature,authorization{from,to,value,validAfter,validBefore,nonce}}}`; sign EIP-3009 TransferWithAuthorization with viem from a fresh key) — CDP rejects with a structured `VerifyError` (`invalid_exact_evm_payload_signature` / `invalid_payload`) visible in runtime logs. Gotcha: x402's `verify()` THROWS on facilitator 400s, so prod returns HTTP 500 (not a graceful 402) for rejected payments — treat 500+VerifyError-in-logs as "reached CDP", not a crash of the challenge lane.
- R2 on prod: this VM can't reach *.r2.cloudflarestorage.com; `media.wzrd.tech` is reachable. The only no-session R2 write lane is `POST /api/media/publish` with a box `gateway_token` (readable via service role from `boxes`), but it needs the user's ascii.dev box awake — boxes may flap resume→archiving→archived (platform-side), which 500s the publish after ~4min. Quick config discriminator: valid gateway_token + invalid path → 400 `invalid path` iff R2 creds configured (503 `media storage unavailable` iff not), since `r2Configured()` runs before path validation.
- Storefront-kind apps have `publicAccess` (runPublicGateChain) — their loader serves 200 to anonymous visitors by design; use a non-public app (e.g. /kanban → 403) for the private-gate regression.

## V6 shopping (purchase_review / fill tickets) testing with the mock backend
- The whole Needs-you + mini-app purchase_review flow (render, approve, deny) runs end-to-end against the :4545 mock — the deployed Supabase project may NOT have the vault/shopping migrations applied (`vault_items`, `fill_ticket_redemptions` return PGRST205 there), so prefer the mock over real Supabase for V6.
- Seed the mock with: a `users` row, a `vault_items` card row (kind `card`, with `masked`), a `boxes` row (`provider_box_id`, `hosted_url`/`hosted_token`/`api_server_key` pointing back at the mock), and a pending `decisions` row `{kind:"purchase_review", ref:<hermes run id>, payload:{host,summary,item_id,amount_band,card_name,card_masked}}`. Add mock routes: `GET /health` → 200 (hermes health, path is `/health` not `/hermes/health`), `POST /v1/runs/:id/approval`, `GET /boxes/:id` → `{box:{state:"ready"}}`, `POST /boxes/:id/commands` → `{exitCode:0}`, `PUT /boxes/:id/files`, and PostgREST GET/POST/PATCH for `decisions`, `vault_events`, `fill_ticket_redemptions` (409 `{code:"23505"}` on duplicate jti), `agent_runs`, `flush_jobs` (empty is fine).
- Approve ("Fill card" on /home Needs-you or in `/mini/vault`) should produce, in order: `vault_events` inserts `ticket_minted` → `fill_ticket_redemptions` insert (jti/host/band) → `ticket_redeemed` → box command (mkdir/install 600) → `PUT /boxes/:id/files` of `.hermes/vault/.tickets/<item_id>.json` (claims only, no card value) → `fill_approved` → hermes approval `{approved:true}` → decisions PATCH `status:"approved"`. Deny/Dismiss: only `fill_denied` (`<host>:owner_denied`), hermes `{approved:false}`, PATCH `dismissed` — no redemption/file write.
- `/mini/vault` mini-app links can be minted with curl: `POST /api/mini/link {"app":"vault"}` with the `air_session` cookie; rewrite the returned URL host to localhost:3999.
- Gotcha: `pkill -f mock4545` from an exec command whose own command line contains the literal `mock4545` kills the shell itself (exit -1). Use a bracketed pattern (`pkill -f "mock[4]545"`) in a separate call from the restart.

- App lives in `apps/web` (npm workspace). Build: `(cd apps/web && npm run build)`; serve prod build: `(cd apps/web && npx next start -p 3999)`. A `next start` on port 3999 may already be running — check `curl -s -o /dev/null -w "%{http_code}" http://localhost:3999/` and compare `.next/BUILD_ID` mtime with `git log -1 --format=%ci` to confirm the build matches HEAD.
- Restart gotcha: `pkill -f next-server` can miss the running `next-server` process and the old build keeps serving — verify with `ss -ltnp | grep 3999` and kill that PID directly before restarting.
- When restarting the server, reuse the previously generated `SESSION_SECRET`/`MINIAPP_SIGNING_KEY` (persist them to files, e.g. under `/tmp` or `~/.airv2-test-env`) so previously minted mini-app cookies/tokens stay valid across restarts.
- To test API route auth contracts (401/400 vs 500) without real credentials, start the server with dummy env vars: `SUPABASE_URL=https://fake-project.supabase.co SUPABASE_SERVICE_ROLE_KEY=dummy SESSION_SECRET=<random> ... npx next start -p 3999`. `serviceClient()` constructs without network I/O, so routes exercise their full auth logic and only fail when they actually query Supabase (which typically resolves to 401, not 500). Set every `required()` var from `lib/env.ts` to a dummy value. With a known `SESSION_SECRET` you can also mint valid/expired/typ-confused HMAC tokens in a `/tmp` script (mirror the `payload.b64url + "." + HMAC-SHA256` scheme in `lib/auth/desktop.ts`) to probe bearer-token routes. `npx tsx` can import `lib/auth/*.ts` directly for library-level token lifecycle tests.
- No `.env` files exist locally, so backend-dependent paths fail: `/api/auth/login` returns 500 (login UI shows inline "could not send code"), `/api/me` returns 401, and any Supabase-backed server page (e.g. `/@handle` contact card) throws a 500 "Application error". Authenticated `/home` dashboard, PromptInput composer, and mini-app webviews are unreachable without Supabase env + a real account.
- `/home` is a client component that fetches `/api/me` and does `router.push("/login")` on 401 — test the redirect through the browser URL bar, not curl (curl on `/home` returns 200 shell HTML).
- Secret-leak scans: grep rendered HTML (`curl /` and `/login`) and `.next/static` chunks for model names / `sk-` keys. Note: dither-kit uses CSS variables named `sk-image-*` — these are NOT secrets. Include `/api/voice/transcribe` responses in the scan surface: its error and success bodies must never echo the STT key, base URL, model name, or any audio bytes (audio is transient per C18 — no Storage/Postgres write to check for content, but scan the JSON responses and logs).
- Speed tier labels (Fast/Balanced/Deep) live in `apps/web/components/prompt-input/PromptInput.tsx` and appear in `.next/static/chunks/app/home/page-*.js`.
- Dark mode: the app relies on `prefers-color-scheme`; the test box has no GNOME schema (`gsettings` fails), so OS-level dark emulation isn't available — verify the `prefers-color-scheme:dark` token mirror in the built CSS instead, or find another emulation path.

## Reaching the authenticated /home dashboard without real Supabase
- You can fully exercise the authenticated dashboard (PromptInput, chat relay, voice) by pointing the dummy env at a local **mock backend** that stands in for Supabase PostgREST + Hermes: a small Node HTTP server (e.g. on :4545) answering `GET/POST /rest/v1/<table>` (return `[]`/inserted row; log inserts to a file for server-side assertions like `agent_runs.trigger`), plus the Hermes run/SSE endpoints used by `lib/chat/relay.ts`. Set `SUPABASE_URL=http://localhost:4545`, `HERMES_BASE_URL=http://localhost:4545`, etc., and mint an `air_session` cookie with your known `SESSION_SECRET` — `/api/me` then succeeds and `/home` renders.
- Rate-limit style checks that count `cost_events` rows can be driven by making the mock read its count from a file (e.g. `/tmp/stt_count.txt`), letting you flip 429/200 deterministically.

## Voice input (M13) UI testing

## Vault surface (V2) testing with the mock backend
- The Vault tab, `/api/vault*` routes, and the `/mini/vault` mini-app can be fully exercised against the local mock (:4545) by extending it to emulate: PostgREST tables `vault_items`, `vault_events`, `vault_managers`, `miniapp_redemptions`, `boxes`, `users`; Box API `POST /boxes/:id/commands` (implement a tiny in-memory `air-vault` CLI: `set/get --field --reveal/delete`) and `POST /boxes/:id/files` (vault inbox writes); Hermes `GET /hermes/health` → `{"ok":true}`. ## V9 mini-app store (mini origin) testing

Browsing `http://mini.localtest.me:3999/` then hits the store home; `localhost:3999` stays the main app. Main-host `/mini/*` 308s to the mini origin; mini-host `/mini/<app>?t=x` 301s to `/<app>?t=x`.

Management API `POST /v1/projects/imkbxdsxfgmkylbgaygv/database/query` works with curl but 403s (error 1010) from python urllib's default User-Agent.
- Gotcha for local browser testing: mini-origin session cookies (`mini_<app>`, `mini_store`) are `Secure`, so Chrome won't store them over http on `mini.localtest.me` — verify the post-redemption render and replay-403 with curl by passing the Set-Cookie value manually.

## Full-bleed overlays inside the onboarding deck (cinematic intro, PR #314)
