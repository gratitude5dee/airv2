# Zap to storefront: from a generated image to a buyable listing

A Zap can end in a live product on your air storefront. The Zap generates the
product art, stages a catalog listing inside your box, and files a decision.
You approve it once in Needs you, and the listing is buyable through Stripe
Connect. The Zap never publishes and never charges: it only stages.

## Run it

```bash
$ npx @wzrdtech/zap run merch-drop --json    # plan only, nothing is written
$ npx @wzrdtech/zap run merch-drop --live    # stages the listing in your box
```

`--json` prints the plan. `--live` is required to write the catalog and file
the decision. Two templates ship in
[gratitude5dee/zap](https://github.com/gratitude5dee/zap): `zap-merch-drop`
(a `physical` listing) and `zap-event-ticket` (an `event_ticket` listing that
mints a ticket code on purchase).

## What happens, step by step

1. **`image.gen`** renders the product art. The Zap uploads it with
   `POST /api/media/publish` (`apps/web/app/api/media/publish/route.ts`),
   which returns a public R2 URL under `R2_PUBLIC_BASE_URL`
   (`https://media.wzrd.tech` by default). Only URLs on that host survive
   publish; a raw provider URL (for example `fal.media`) is dropped to `null`.
2. **`commerce.stage_listing`** runs inside your box and does two things:
   - merges an entry into `~/.hermes/miniapps/shop/catalog.json`
     (`{ "items": [...] }`), and
   - `POST ${OPENAI_BASE_URL%/api/gateway/v1}/api/miniapps/commerce` with
     `Authorization: Bearer $OPENAI_API_KEY` (the box gateway token) and body
     `{"action":"publish_catalog"}`. That route
     (`apps/web/app/api/miniapps/commerce/route.ts`) calls
     `requestCatalogPublish`, which files one pending `shop_publish` decision.
     Re-running the Zap reuses the open decision instead of piling up.
3. **You approve** the decision in Needs you. `POST /api/decisions` with
   `action: "approve"` (`apps/web/app/api/decisions/route.ts`) calls
   `applyCatalogPublish` (`apps/web/lib/commerce/catalog.ts`), which reads the
   box catalog, runs every entry through `sanitizeCatalogItem`, and upserts
   `storefront_products`. Catalog entries that disappeared are deactivated.
4. **A buyer** opens your storefront mini-app and taps Buy. `startCheckout`
   (`apps/web/lib/commerce/checkout.ts`) reads the price from the projected
   row, records a pending order, and creates a Stripe Checkout Session as a
   direct charge on your connected account.
5. **Stripe** sends `checkout.session.completed` to
   `apps/web/app/api/inbound/stripe/route.ts`. `fulfillCheckoutSession` flips
   the order to `paid` exactly once, decrements inventory, and mints a
   `ticket_code` when the product `kind` is `event_ticket`. You scan it with
   `checkInTicket`; it checks in once.

## The catalog entry a Zap writes

```json
{
  "key": "neon-wolf-tee",
  "kind": "physical",
  "name": "Neon Wolf Tee",
  "description": "Generated by the merch-drop Zap.",
  "imageUrl": "https://media.wzrd.tech/u/casey/media/abc123-product_art.png",
  "priceCents": 3500,
  "inventory": 100,
  "active": true,
  "source": { "zap": "merch-drop", "runId": "run_xxx", "stepId": "listing" }
}
```

For tickets, set `"kind": "event_ticket"` and `inventory` to the ticket count
(or `null` for unlimited). `source` is Zap metadata; `sanitizeCatalogItem`
ignores it and it never reaches `storefront_products`. Fields are camelCase;
the snake_case aliases `price_cents` and `image_url` are accepted, and
camelCase wins when both are present. The sanitizer also enforces: `key`
matches `^[a-z0-9][a-z0-9_-]{0,63}$`, `priceCents` is an integer from 1 to
10,000,000 (one cent to $100k), `name` is at most 200 characters, and
`description` at most 2000.

## Invariants

- **No Zap step ever charges.** The only path that moves money is the
  decision-gated Stripe Connect direct-charge flow in
  `apps/web/lib/commerce/checkout.ts`, and it runs when a buyer checks out,
  never when a Zap runs.
- **Publish is decision-gated.** `publish_catalog` files a `shop_publish`
  decision. Nothing reaches `storefront_products` until you approve it.
- **Prices are never client-supplied.** `startCheckout` takes a product key
  and a quantity. `amount_cents` comes from the projected row, and the
  Checkout Session gets the same per-item price.
- **Only public data is projected.** Image URLs must live on R2; everything
  else is dropped. The catalog is the box-side source of truth.

The tests for this flow live in
`apps/web/lib/commerce/commerce.test.ts` under
`describe("Zap-staged listings (commerce.stage_listing)")`. Run them with
`(cd apps/web && npm test -- --run lib/commerce)`.
