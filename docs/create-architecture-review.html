01 · System map

How /create is wired today

Two entry points feed one Box. iMessage turns run in the owner's main Hermes session (air-main) with the chat model. Web turns run in a per-app session (air-create-<app>) on the Create model tier. In both cases the model reads the create-miniapp skill and drives the pipeline itself: it shells out to air-create, which curls /api/create/* one step at a time. Select any box for its files and failure notes. Select a failure below to highlight where it lives.

Selected component

Skill + air-create CLI

infra/template/skills/create-miniapp/

The model reads SKILL.md, a stage-by-stage script, and runs air-create plan, confirm, build, qa, test and release in order. Each one curls a control-plane route with the Box's gateway token. Only this CLI writes the intake events plan_written and confirm.

The first event it sends, plan_written, is illegal from asking and returns 409. The CLI swallows that 409 when --deliver is set, so the model believes the plan step succeeded.

02 · Failure register

Where it breaks, in the order an owner hits it

F1 to F4 each block every app on their own. F5 is invisible today and blocks the moment F2 is fixed. Select a row to light up its components on the map.

F1

Nothing moves the intake past asking

Blocker

The stage machine has one exit from asking: an owner_reply event. On iMessage nothing sends it. The Box's first move is plan_written, which returns 409, and the CLI hides that 409 when it delivers the plan. confirm then 409s too. No code path ever sends build_started, build_ok, qa_ok, tests_ok or dev_live, so even a perfect run could never reach dev_ready, and finalize requires dev_ready.

Evidence
The only intake in production has sat at asking since 18 Sep. There are zero intake ops events.
Code
lib/create/intake.ts:136 (asking → owner_reply only) · air-create:474-480 (409 swallowed) · lib/create/finalize.ts:311 · no callers of advanceIntake in build, qa or release
Fix
Derive stages on the server from facts (build row, QA row, dev_version) and accept plan_written from asking.
F2

The app-origin lane is off, so drafts can't be previewed

Blocker

deployStaticVersion returns early unless the signing key, the Cloudflare account and token, and the manifest KV id are all set. Builds still succeed and store bundles in R2, but no draft Worker ever exists. /api/create/preview-link returns 503, so air-create qa and test exit before opening a browser. The dev release gate needs QA ≥ 70 and all tests passing, so it can never pass. The web studio's preview pane is blank for the same reason.

Evidence
0 of 33 versions carry a worker_sha256. 0 QA scores and 0 test results exist. There are no create.qa ops events.
Code
lib/functions/deploy.ts:73-79, 271 · lib/create/preview.ts:15-16 · app/api/create/preview-link/route.ts:50-52
Fix
Configure the lane in production and deploy the Dispatcher with real KV ids. Make /create refuse up front, with one clear line, when the lane is off.
F3

A 120-second chat turn is asked to run the whole build loop

Blocker · iMessage

SKILL.md step 4 tells the model to write goal.md, confirm, build, QA, test, fix and release "in the same turn", for up to six build rounds. The flush job stops any Hermes run that hasn't finished its reply by 120 s. It then sends "I need a little more time", replays the same burst after a growing backoff, and kills the replay at 120 s again. The build itself is quick (median 4.8 s in production). The time goes to the loop around it: source edits are model generations, QA drives a browser through six passes, and tests add more.

Evidence
In the last 14 days, 37 of 114 iMessage turns ended as first_response_failed. Only one fix has landed since V12, and it raised the deadline from 45 s to 120 s for exactly this reason (95924dc).
Code
lib/orchestrator/flush.ts:95-96, 1467-1520, 555 · SKILL.md §6 step 4 · air-qa.py:113
Fix
Take the loop out of the turn. "yes" confirms and enqueues a job, and the owner gets a reply in seconds.
F4

Hyphenated app names can't be released or finalized

Blocker

release, finalize and icon accept a bare app name or a flat <user>-<app> slug, and they tell the two apart with splitPublishedSlug. An app named october-tour parses as user october, app tour, and returns 404. The intake builds names by joining up to three words with hyphens, so nearly every /create app is affected.

Code
app/api/create/release/route.ts:69-71 · lib/create/finalize.ts:276 · lib/create/intake.ts provisionalAppname
Fix
Look up the owner's app by app name first, and fall back to the flat slug only when that misses.
F5

The Dispatcher redirects every preview and dev link to a 404

Hidden until F2 is fixed

Hand-off URLs land on /__air/enter?t=…. After spending the one-time token, the Dispatcher 303s to url.pathname, which is still /__air/enter. The static stub serves assets with not_found_handling: "none", so that path 404s. The token is gone, so a reload won't help. This was logged as MS-20 in review.md before V12 and is still open.

After redeeming the token, redirect to / (or a signed next path) whenever the request path is the enter path.
F6

The progress card never starts

Major

The relay is started once, at the start of each flush turn. It only starts when an intake is already in confirmed to testing with an app_id. Stages never get there (F1), and app_id stays null for a new app until finalize. The build also happens inside the "yes" turn, which began at plan_sent. The web Progress pane shows 0% for any stage before confirmed.

Attach the relay to the build job rather than the chat turn.
F7

Major

iMessage plans and builds in air-main on the chat model. That spend isn't charged to the project budget, and the "Astra plans, GLM builds" split never applies. The Plan pane's Build this button posts confirm without sending the agent a turn, so the Box never hears "yes". A project started in Messages can't continue on the web with its context.

04 · Time budgets

The build loop doesn't fit in one chat turn

Everything below is drawn to one scale. The skill asks for confirm → build → QA → test → release inside the "yes" turn. On iMessage that turn is stopped at 120 s and replayed after a growing wait. Each replay is stopped again, and the owner never gets a reply. The build isn't the slow part. The model's edit turns and the browser passes around it are.

05 · Diagnosis

Why a well-specified system produced this

The spec is careful and much of the code is good. The failures come from four structural choices. Each would keep producing new bugs of the same kind even after the ten above are fixed.

Root cause A

The model drives the state machine

Every stage change happens only if the LLM runs the right shell command, in the right order, and it succeeds. The control plane accepts one narrow order of events and rejects the rest, and the CLI hides some of those rejections. Whenever the model skips, retries or reorders a step, the stored state silently stops matching reality.

Root cause B

A chat turn is used as a job runner

A request/response turn with a 120-second budget is holding a loop that runs for minutes, fans out into network calls, and must survive retries. Nothing durable owns that work. A retry replays the owner's message instead of resuming the job.

Root cause C

Built in parallel against mocks, and never run end to end

Six lanes were built in parallel, each tested against fakes of the others. The code comments show it: "lane A owns the writer". MC0, the milestone meant to prove the seams on a real line and a real Box, was skipped. The only visual evidence is a screenshot set driven by route mocks.

Root cause D

Missing config fails silently

Every missing piece of config turns into a 503 or a skipped step, and nothing reports whether the feature can work at all. Production looks deployed while the path is inert, and the owner learns this five steps into a conversation.

06 · Target architecture

Move the build loop from the model to the control plane

Keep the model for the parts that need judgment: questions, the plan, and edits to source. Give the loop and the state to deterministic code. Only two things change between the diagrams: which component holds the loop, and how the stage gets written.

The worker owns the loop

A create_jobs row is claimed and advanced by the same claim/deadline pattern flush_jobs already uses, or by Vercel Workflow. Every step is idempotent and resumable, and a retry resumes the job instead of replaying the owner's message.

Stages are derived from facts

stage = f(plan_sha256, confirmed_at, latest build, QA row, dev_version). Events are kept only for owner intents (confirm, revise, ship, cancel), and they're idempotent.

One session per project

Both surfaces talk to air-create-<app> on the Create tier, carrying the marker. air-main hands off and stays conversational, so budget, the model split and context are the same on both surfaces.

Check readiness before starting

/create checks readiness first: storage, the app-origin lane, the link host, the provider key and the Box's skill version. If a lane is off, the owner gets one clear line at the start instead of a dead end at step six.

07 · Fix plan

Three phases, sequenced so each one is testable

Phase 1 gets the golden path working with small, contained diffs. Phase 2 is the architectural change that stops this class of bug from coming back. Phase 3 makes the system prove itself continuously.

Phase 1 · Unblock the golden path

small diffs · days

  1. Turn on the app-origin lane in production (APP_ORIGIN_SIGNING_KEY, CLOUDFLARE_ACCOUNT_ID, CLOUDFLARE_API_TOKEN, CF_MANIFEST_KV_ID). Deploy the Dispatcher with real KV ids, and fix the enter redirect in the same change. F2 · F5

    a build writes worker_sha256, the preview opens in a browser, and one QA score lands.

  2. Have the server write intake stages: the build route records started/ok/fail, the QA route records qa_ok/tests_ok, and release records dev_live. Accept plan_written from asking, and have the flush hook record the owner's reply while an intake is at asking. F1

    a route-level test drives the real handlers from asking to dev_ready.

  3. Resolve app names before flat slugs in release, finalize and icon. F4

    air-create release october-tour dev finds the owner's app.

  4. Set LINK_HOST_ENABLED=true and make promoteToDev refuse when it's off. Set the app's app_id on the intake at the first build so the relay can find it. F8 · F6

    a dev URL returned by release serves the app to a logged-out browser.

Phase 2 · Move the loop out of the chat turn

the structural fix · about a week

  1. "yes" in Messages and Build this on the web call one endpoint that confirms and enqueues a create_jobs row. The chat turn replies within seconds. F3 · F7

    no /create turn runs longer than 30 s.

  2. A pipeline worker runs a builder turn in air-create-<app> (awaited through the existing 800 s event stream), then build → preview → QA and tests (triggered in the Box by runCommand) → dev release. Each step records a fact, retries are bounded, and the failed stage replaces silent stalls. A · B

    killing the worker mid-build and restarting it resumes from the last recorded fact.

  3. Attach the progress relay to the job. The web Progress pane and the iMessage card read the same job. F6

    twelve or more card updates for one build, with no new bubbles.

  4. Route iMessage /create into the project session on the Create tier, with the marker on both surfaces and #stage on the model string. F7

    admin Tokens shows Astra and GLM spend for one intake started in Messages and finished on the web.

Phase 3 · Make it prove itself

ongoing

  1. Automate MC0 as a nightly smoke test: a synthetic owner on a staging Box runs /create to a dev link, and the test asserts every stage timestamp. C

    a red nightly run blocks the release channel.

  2. Add a /api/admin/create/health readiness report covering storage, the app-origin lane, the link host, GMI, Dispatcher health, and the skill version per Box. /create refuses up front when any of these is off. D · F10

  3. Add abandonStale and expireDevReleases to /api/cron/sweep, and write relay ops_events. Deploy Workers from CI with KV ids from secrets. air-create sends its skill version and the control plane rejects versions it can't serve. F8 · F10

  4. Close the gaps in what the Box receives: write intake/prompt.md at hook time, sync templates, snapshot tests for the locked-test guard, mint guest test URLs, and fall back to a card when the owner has no iMessage thread. F9
