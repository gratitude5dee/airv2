# air 2.0: Product and Engineering Review (September 2026)

**Handoff for Astra Ultra.** This document is the build brief. Every finding carries a stable ID, a severity, an effort estimate and `file:line` evidence in this repository at commit `bb82c05`; every section ends with an ordered plan and the decisions only the product owner can make. Read §0 and §3 first, then the section for the workstream you own. Appendix A indexes all 249 findings with their verification status; Appendix B collects the questions only the product owner can answer (the defaults to assume if no answer arrives are in §12); Appendix C lists what this review did not measure, so no number here is mistaken for one that was.

**Scope requested by the owner:** the memory implementation, user-perceived latency, mini-app and Spectrum (iMessage) optimisation against `photon-hq/create-spectrum-project`, task completion across apps including the wzrdmail cutover, and the replacement of the Composio social integration with a self-hosted stack modelled on `gitroomhq/postiz-app`. The adCP-Demo repository was reviewed and then excluded at the owner's request; nothing below refers to it.

**Method.** Ten independent deep-read reviews (one per dimension), each P0/P1 finding then adversarially verified by independent agents (code accuracy; real-world impact and invariant fit), a completeness critic per dimension whose corrections were applied and whose additional findings were accepted only after the author checked them against the code (Appendix A marks these *critic-evidenced* or *author-verified*), an independent fact-check of every number and citation in the draft, an implementation-lead read of the whole draft, and the author's own spot checks of every headline claim. One claim was refuted outright and removed (that the default model family collapses skill routing: the eval runs that appeared to show it were served by the fallback provider); everywhere else severities and wording were corrected where verification showed the mechanism narrower than first stated. The pinned Hermes source (`29112bef`, cloned for this review) was read to settle the questions the airv2 code left open: server-side transcript loading (§4.2), prompt rebuild per run (§4.2), the events stream's lack of replay (§5.2), per-session run concurrency (§5.2), and the approval and steer endpoints (§7.5). One correction applies across the document: every per-case latency in the committed eval reports includes a fixed 20 s harness sleep before the measurement is taken (WEB-24, §5.4); the corrected agent-time figures are used throughout and the raw figures are quoted only with that caveat. The August 2026 review (`docs/review-2026-08/`) and its tickets were read first; items still open there are noted, not re-reported.

**Conventions.** Severity: P0 breaks users, money or security now; P1 materially degrades the product (latency, task completion, memory) or blocks a stated cutover; P2 worth scheduling; P3 hygiene. Effort: S under a day, M one to three days, L more than three days. Where two reviewers found the same root cause from different sides, the body keeps both IDs and Appendix A names the canonical one; file one ticket per canonical ID. No finding in this review is P0: nothing is breaking users, money or security right now (one row, WZ-01, becomes P0 the moment `MAIL_PROVIDER` is flipped). The 74 P1s are what degrades the product today or blocks a stated cutover; §12 schedules all of them by ID except three that carry no ticket of their own: CA-03 and CA-17 are umbrella rows covered by §7.5 and §5 respectively, and CA-18 is a commercial decision, not engineering work, so it sits in §12's decision table.

## 0. TL;DR: the eleven things to do, in order

The codebase is disciplined and its security boundaries hold: C2, C4, C10, C15 and the allowlisted box proxy were re-verified everywhere we looked. ## 2. The system as built: one agent, or several lanes?

For one inbound iMessage, cognition is distributed like this (REAL = shipping, SHADOW = runs but nothing consumes it, MISSING = specified, not built):

```
perception   Spectrum webhook → HMAC → parse → resolveLine/handle → dedupe → onboarding → trust tier     REAL
routing      tier 0/1/2 resolved before any compute; tier 2 never wakes a box; tier 1 runs in the       REAL
             owner's air-main session with no identity in the prompt (CA-20)
lanes        prewarm ‖ Spectrum #1 → markRead → typing → quick-ack completion (fast, no tools)           REAL
             2.5 s debounce → claim → Spectrum #2 → drain → /slug card lane → /imagine creative lane      REAL
             → wake (cold: shared-bridge completion + holding line + carry + backoff)                     REAL
             → @bot delegation → history replay (≤60 msgs, hold-and-retry if empty)                       REAL
memory       Hermes MEMORY.md/USER.md (always in prompt) · OpenViking (only if the model calls it)        REAL / thin
             · Mitosis (display only) · onairos.md · connected-tools.md · SOUL.md (12 header-guarded blocks carrying 14 `##` sections; only 10 blocks reach existing boxes, TC-19)
agent loop   Hermes api_server run + SSE; control plane consumes message.delta / run.completed only       REAL, thin
tools        terminal, browser, files; MCP: composio proxy, mail, openviking, daytona, masterkey;          REAL
             text markers [card:] [send-file:]; taskrouter :1917 GGUF classifier                          SHADOW
side effects (a) Hermes smart_policy pause + /v1/runs/{id}/approval                                       REAL
             (b) decisions table (19 kinds) filed by the agent over HTTP; draft-sweep backstop             REAL
             (a)→(b) bridge for social_post from iMessage: broken (ref is null)                            BUG
delivery     first paragraph streams in place, ≤5 bubbles, tapback probe, native files, cards            REAL
             web: raw SSE, markers not stripped, no command lane                                          DIVERGENT
receipts     agent_runs row inserted after the stream with outcome 'completed' unconditionally;           NOT TRUTHFUL
             cancelled and failed turns write no row (CA-24)
failure      mini-app and creative lanes send a failure line; the core lane throws and sends nothing      SILENT LOSS
learning     air-learningd + ledger in the template; no trace_id minted, nothing calls turn.completed     MISSING
```

Two voices answer every owner burst (quick-ack, agent) and a third (the bridge) when the wake fails; four session namespaces (`air-main`, `email:<thread>`, bot chat, `air-<thread>`), and `air-main` itself has four writers (web, desktop, schedules, and tier-1 contacts, who run inside the owner's session with no identity in the prompt: CA-20, CA-22) with no concurrency policy; three memory substrates plus the un-indexed context files (§4.1); three instruction channels (SOUL.md, the 21 template plus 17 hub skills counted in CA-19, connected-tools.md); four tier vocabularies (`TIER_MODELS`, `CREATE_TIER_MODELS`, task-router tiers, delegation `fast`); three schedulers (`agent_schedules`, in-box Hermes cron, of which the control-plane calendar-sync job is the one verified instance, bot routines); two approval mechanisms; and two surfaces with different pipelines. None of this is wrong in isolation. Together it means there is no single place that knows what the agent is doing, what it knows, or whether it finished.

What is missing from a real agent loop: an explicit task/plan object across turns; verification (outcome is `completed` on stream end in all three lanes); progress reporting on iMessage (ARCHITECTURE §2.6b's "one card that updates as work progresses" is unbuilt; `tool.started` events are dropped); consistent interruption (web stop for the default agent only; on iMessage every new message cancels the in-flight reply, so a "thanks" mid-stream truncates the answer); proactive behaviour (no Brief, three schedulers); error recovery that is asymmetric by lane (mini-app and creative lanes send a failure line, the core lane sends nothing and the burst is gone; CA-21); and an approval loop open at both ends (CA-23).

### The thesis vs delivered

"Own computer" is the most real promise: one Box per user, desktop stream, vault, headed browser, snapshots. "Own inbox" is real and mid-cutover, but email cognition is isolated per thread with no owner context. "Own number" is the weakest: neither Photon tier gives per-user lines by default (ARCHITECTURE §7.1), provisioning makes the line optional and falls back to sender-handle routing on the shared pool, and the stop/resume model caps out around 150 users on the start ceiling (§6.2). The evals say the agent itself is the bigger gap than any channel: execution 0-25% on the five runs in §7.1's table (0-29% across all committed reports, on denominators of one to seven cases), zero to five decision rows per run (four committed reports record none; the maximum, 5, is over run7's 42 cases), routing from 92% (Aug 26 run4) to 83-84% (Sep 1 full runs), context use from 63% to 50%, 24-25k prompt tokens per gateway call, and per-case latency of 60.0 s mean, 44.3 s p50, 155.2 s p95 on the run6 report (`results/2026-09-01T-run6-fixes/report.md:19`). Every per-case latency in the committed reports includes the harness's fixed 20 s settle (`evals/agent-suite/run.ts:41`; see WEB-24): subtracting it, run6 is about 40 s mean and 135 s p95 of agent time, and the headline `wzrdmail-full` figures (35.9 s mean, 22.3 s p50, 51.7 s p95; `results/wzrdmail-full/report.md:19`) correct to roughly 16 s, 2 s and 32 s. Comparisons across runs are caveated: the runs differ in model family and box seeding, and the committed report was produced against the founder's live box (CA-29).

## 4. Memory

### 4.1 As built

Three substrates exist, and only one of them is in the model's context on every turn.

| Layer | Where it lives | Writers | Readers | In the prompt? |
|---|---|---|---|---|
| (a) Hermes native memory | `~/.hermes/memories/MEMORY.md` + `USER.md` (USER.md capped at 1,375 chars) | Hermes memory tool; the owner via Settings/Context; **the control plane splices an Onairos persona block into USER.md** (`lib/onairos/sync.ts`) | Hermes system prompt every turn; owner UI; admin export | Yes, always |
| (b) OpenViking deep memory | loopback server `127.0.0.1:1933`, workspace `~/.openviking`, pinned `openviking[local-embed]==0.4.16` | `lib/imessage/ingest.ts` (per upload chunk), `lib/onairos/sync.ts` (onairos.md), `lib/context/importer.ts` (Dictionary.MD, agent-import), the agent via MCP `remember`/`add_resource` if a skill nudges it | the agent via MCP `find/search/read`; Persona mini-app via `ovctl recent`; admin export | **No.** Only if the model decides to call a tool |
| (c) Cortex / Mitosis | third-party office, credentials in the box `.env` | nothing in this repo writes to it | Persona mini-app via a python heredoc run on the box; the agent can reach the key, which sits in `~/.hermes/.env` (`lib/memory/mitosis.ts:6-7`, `cortex.ts:65`), and the UI tells owners it does (MEM-30) | No, and there is no MCP entry for it |

Four writers touch these stores: Hermes itself, the Onairos splice, the Dictionary subagent, and the OpenViking ingest hooks. The learning plane is not a fifth: `goal.md:58,160` forbid candidates from editing memory, and nothing under `infra/template/learning/air_learning` touches SOUL, USER.md, MEMORY.md or OpenViking.

"Every turn" for layer (a) is verified against the pinned Hermes: every `/v1/runs` call constructs a fresh agent (`gateway/platforms/api_server_runs.py:720`, `gateway/platforms/api_server.py:3142`) and the prompt builder always includes USER.md (`agent/system_prompt.py:933`); `sessions.system_prompt_hash` is a stored record kept by `COALESCE` (`hermes_state.py:6413-6415`), not the prompt source, so the NULL-ing in `infra/template/sync-box.sh:507-525` is harmless and an edit to USER.md or MEMORY.md is visible on the next turn. Nothing in this repo guards that property across Hermes bumps (MEM-23).

Plus the per-turn transcript replay: `lib/hermes/history.ts` fetches the `air-main` transcript through the hosted proxy (no `limit` parameter, so the endpoint's default page of the latest 500 rows) and ships the last 60 merged messages as `conversation_history` on every run (`lib/orchestrator/flush.ts` `replayHistory`, `lib/chat/relay.ts` via `createRun`). The premise in `history.ts` ("the runs endpoint does NOT load the stored transcript") is stale for the pinned Hermes: `gateway/platforms/api_server_runs.py:600-603` loads the session's own transcript server-side whenever the client omits `conversation_history`, and `GET /api/sessions/{id}/messages` accepts `limit` (max 500), `offset` and `order=latest` (`api_server.py:4499-4548`). The control plane is doing, on the critical path and with a 60-message cap, what the box already does for free.

What the spec (`docs/memory-upgrade.md`) promises and what ships:

| Promise | Status |
|---|---|

### 4.3 Target architecture and work plan

The honest current state, in the spec's own words, is "a good profile and a pile of unindexed context next to it". The fix is not a fourth substrate. It is to (1) make the archive's inputs complete and recallable, (2) make layer (b) actually participate in every turn, in both directions, (3) give the system one write policy and one consolidation loop, and (4) measure recall.

**Target: four memory roles, two stores.**

| Role | Store | Write policy | Read policy |
|---|---|---|---|
| Working memory (this conversation) | Hermes session transcript, loaded by Hermes itself (MEM-16) and capped box-side; `air-main` holds human-initiated turns only, automation runs in purpose sessions (MEM-24) | Hermes | every turn |
| Profile (stable facts about the owner) | `USER.md` (Hermes is the *only* writer; Onairos and the consolidator write `viking://user/profile-digest` and Hermes's own memory tool decides what reaches USER.md; no SOUL instruction rewrites the prompt file, since a layer (b) writer to USER.md is the `docs/memory-upgrade.md:114` escalation) | Hermes memory tool | every turn |
| Episodic + semantic archive | OpenViking: raw resources (iMessage threads by `<thread>/<yyyy-mm>` as markdown, email threads, imports, onairos.md) + extracted memories | ingest hooks (idempotent, content-derived ids, durable across stops) + a written policy (a durable fact goes to `remember` plus a one-line `memory` pointer, MEM-17) + nightly consolidation (`remember` over the day's transcripts, dedupe, `forget` superseded) | **box-side recall by default**: the skill and a `## Your memory` SOUL block, or a Hermes pre-turn hook in the pinned fork, calling `find` with `target_uri: viking://resources/context`, gated by a cheap intent regex (person/place/date/preference/"remember"/"last time"). ## 5. Latency: the iMessage path

### 5.1 What the user waits on

Spec targets (`docs/goal-air2.md`): typing indicator "immediately on receipt"; reply within 15 s warm, 60 s cold. What the code does, in order, for one inbound message:

**Before the 200 to Spectrum** (all sequential, `app/api/inbound/imessage/route.ts`): HMAC verify → `lines` select → (`handles` select on a shared line) → `inbound_events` insert → `provisioning` select → `handles` select (+ `senders` select/insert for non-owners) → (`connections` select when Onairos is configured) → `batch_queue` insert → `imessage_destinations` upsert → `schedule_flush` RPC. Seven to eight Supabase round trips, ~0.4-0.6 s at ~50 ms each, before the ack that C8 says should come first.

**After the 200** (`after()`, function held for the whole turn, `maxDuration = 800`): `prewarmBox` (fire-and-forget resume) ‖ `createSpectrumSender()` #1 (two HTTPS calls to Spectrum Cloud + a fresh gRPC client) → `markRead` (getMessage + send) → `startTyping` → `isBurstStart` (two counts in one round trip) → marker insert → `quickAckReply` (self-HTTP to the gateway, 2.5 s cap, 60 tokens) → `sendText` → marker update → sleep to `run_at` (2.5 s from enqueue) → `claimFlush` → `runFlush`: `createSpectrumSender()` #2 → four drain queries → lane regexes → `ensureBoxAwake` (boxes select, update, `getBox`, health probe; on a cold box: resume, `waitForBox` at 5 s granularity, health loop at 5 s with `host url --timeout 120` on each miss) → `listBots` → `ensureSession` → GET full transcript → `createRun` with 60 messages → SSE → tapback probe (needs 9+ chars) → first bubble.

**Derived budgets** (derived, not measured; assumptions: Supabase ~50 ms, Box API ~300 ms, hosted proxy → Hermes ~200 ms, Spectrum Cloud ~250 ms; no region is pinned in `apps/web`, so every per-hop figure is an assumption):

Warm trivial turns are already fast; the cost lives in cold starts, in the tail, and in the iMessage-only steps the derived budget adds (Spectrum init, ack lane, debounce, wake loop), none of which is timestamped: hence LAT-15 (instrument) is the first item of the plan.

### 5.3 Target: typing under 1 s, first real token under 5 s warm, under 20 s cold

The design is right; the implementation serialises everything and re-does setup work per message. Ordered plan:

1. **Instrument before optimising** (LAT-15): a content-free `imessage_turn_metrics` row per message (received, acked, typing, ack, claimed, box_ready, run_created, first_delta, first_bubble, completed, warm/cold, `ack_outcome`, `ack_ms`), wake phases logged from `boxes.ts` (resume→ready, ready→route, route→healthy), and an eval mode that drives the signed webhook against a test line. Effort M. The steps below are ordered by expected win; this step supplies the numbers that confirm the order.
2. **Fix the ack lane as one unit** (LAT-17, LAT-18, LAT-06 re-send; all S): pass the ack promise in-process to `flushAfterDebounce`/`runFlush` so the marker carries the real text or nothing (DB markers stay for the cron-retry path only); add a per-family fast slug with the rule "skip the ack when the family has no genuine fast slug"; re-send typing at the three points LAT-06 names. Without this, every downstream latency win makes the double-answer race more likely, not less.
3. **Stream the gateway** (LAT-01, LAT-12): replace buffer-then-replay with a tee: forward every byte as it arrives; fall back to OpenAI only if the upstream stream *closes* without a content-bearing delta and nothing was forwarded (there is no deadline-based fallback: an open stream with no delta yet is simply waited on, bounded by the header timeout). Put `fetchWithHeaderTimeout` (already in `lib/http/timeout.ts`) on dispatch. Effort S for the tee, M with the header contract and tests in §5.4. This alone removes 3-8 s per model call for every default-family user.
4. **One Spectrum sender per turn, then one per warm worker** (LAT-03, LAT-06): pass the webhook's sender into `flushAfterDebounce`/`runFlush`/`sendMarkedCards`; fire `startTyping` before `markRead`; re-send typing every ~25 s while waiting. Then memoise a module-level `Spectrum()` per warm Vercel worker with an idle close, which also removes the five inits a four-message burst pays today. ARCHITECTURE §7.2 names this as the expected evolution. Effort S then M.
5. **Make the wake adaptive and single** (LAT-05/BOX-11, LAT-07/BOX-01, LAT-04, LAT-20/BOX-19, LAT-22, LAT-23, BOX-04): 1 s polls for the first 15 s; run the orchestrator `host url` refresh only after N consecutive misses (log whether the refreshed token ever differs from the stored one to size N); no unit restart before several failed probes spanning a real boot window, never restart `hermes-host` from the orchestrator (BOX-19); `Nice`/`After=` ordering and a chown-only sidecar timer (LAT-20); skip `resume` on a box already in a transitional state; make `prewarmBox` do the full wake, fire it right after line resolution, and cache a per-user in-flight promise so the post-debounce `ensureBoxAwake` joins it and a losing claimant re-arms `stop_after` (LAT-08); wait for `waitForHomeSteady` after a genuine resume; treat an empty replay like a wake failure (LAT-22); keep the in-process `after()` alive across the first retry (re-read `run_at`, re-claim; LAT-04) and move overdue flushes into their own cron route (LAT-23) so the cron is the backstop, not the path. Effort M.
6. **Decide the ack lane** (LAT-02, CA-01): the decision this review recommends is to make it acknowledgement-only now (a fixed template such as "on it: <2-4 word restatement>", no model call, so it can never contradict the real answer and costs nothing), run it concurrently with the flush only with step 2's in-process hand-off in place, and log its hit-rate. Once steps 2-5 bring the warm first token under 5 s, delete the lane entirely: typing plus a fast real path beats a one-liner, and goal-air2 promises exactly one reply. Effort S.
7. **Collapse the DB chains** (LAT-09, LAT-11): one `ingest_imessage(...)` SECURITY DEFINER RPC pre-ack (routing metadata only); `Promise.all` the independent post-claim reads; one `gateway_preflight(token)` RPC returning entitlement + the single provider key actually needed, callable in-process by `completeFast()` with a resolved principal; batch metering into one RPC. Effort M.

### 5.4 The web chat path, the gateway, and the box proxy

#### As built
A web message is two Vercel invocations: `POST /api/chat` does ten sequential network round trips (bots roster, boxes select, `stop_after` update, provider `getBox`, Hermes `/health`, state update, full transcript GET, `POST /v1/runs`, `agent_runs` insert, `armStopAfter`) and returns only a run id; the browser then opens `/api/chat/{run}/events`, which runs `ensureBoxAwake` again (five more round trips) and opens the SSE. About 16 sequential round trips and two invocations before the first Hermes byte, then the gateway's own five sequential DB reads before the provider is contacted. `/home` is a 1,250-line client component with no server data: first paint waits for the bundle, then eight requests fan out, two of them through the box proxy (each paying a full wake check), and on a cold box three invocations run the wake loop concurrently.

The gateway (`app/api/gateway/v1/[...path]/route.ts`, 765 lines) is the one place every model call passes through, which makes it the highest-leverage file in the repo for latency and for honesty about what model served.

None of this path is measured end to end. The gateway's `latency_ms` timer starts after its own pre-dispatch reads (WEB-23) and the eval suite's per-case latency includes a fixed 20 s settle plus two Supabase reads (WEB-24), so both the current median and the gain from the work below are invisible in the numbers the team collects today.

### 7.3 Structural causes

1. **No task object.** The run has no notion of "what was asked"; outcome is the SSE terminal frame (`completed` in all three lanes).
2. **No post-run verification at run close.** Every gate depends on the agent making a second, unverified HTTP call. The one backstop (`draftSweep.ts`, every minute from `/api/cron/sweep`) covers email drafts only, after a 5-minute grace (TC-20).
3. **No single side-effect gate.** `createDecision` types 4 of the 19 kinds; ≥10 raw inserts; 6 of 8 agent-staged kinds never notify the owner on iMessage, so Needs-you fills silently while the owner is texting; the two that do notify drop the second and third card of a turn under a 2-minute cooldown (TC-28).
4. **Skills are the only steering, and they compete** with agent-authored skills that `sync-box.sh` never prunes. The steering also does not reach existing boxes: `sync-box.sh` omits the two SOUL sections written for these failure modes and header-guarded appends never propagate edits (TC-19); bot profiles get none of it (TC-26).
5. **Tool discovery dominates.** Control-plane actions are curl recipes with env boilerplate, so the model spends `tool_search → tool_describe → COMPOSIO_SEARCH_TOOLS → tool_describe` before any work.
6. **Model path.** `fast` and `balanced` both map to gpt-5.6-luna, and tool-bearing calls are pinned to `reasoning_effort: none`; the seeded wzrdmail run shows 281/300 calls at none with ~59 completion tokens each.
7. **Paused runs are invisible.** Hermes smart approvals pause runs (`execute_code`, publishing) that no surface resumes except `social_post`, and `hermesDeltas` cannot tell a paused run from a slow one until `maxDuration`.
8. **The task router is shadow with no consumer; the learning plane has no producer** despite `plan.ts` marking M1 shipped.
9. **The eval measures only the web relay, on a settle shorter than the product's reconciliation** (TC-21, TC-24, TC-20).

## 8. The wzrdmail cutover

### 8.1 As built

`lib/mail/client.ts` is a real seam: every export re-dispatches per call to `lib/agentmail/client.ts` or `lib/wzrdmail/client.ts` by `env.mailProvider()` (`MAIL_PROVIDER`, default `agentmail`), and the type `MailClient = Omit<typeof agentmail, "AgentMailApiError">` forces compile-time parity. The wzrdmail client is a near-copy against `${WZRDMAIL_BASE_URL}/v0`. One inbound route verifies with the *active* provider's `whsec_` only, normalises the two envelopes, resolves `to[]`, dedupes on `(svix-id, message_id)`, acks, then runs the turn in `after()`. Provisioning runs only from `setUsername`: pod → inbox → retire old primary → insert row → `ensureWebhook` → draft-only key → rewrite `.hermes/.env` (active prefix only) → patch `mcp_servers` → `sudo systemctl restart hermes-gateway`. That wiring is a one-shot side effect of `provisionEmail`: a box replacement (`switchEnvironment` → `finishSetup`) installs skills, Composio, MasterKey and Daytona but never mail, and nothing reconciles it afterwards (WZ-16).

What was validated on staging (`evals/agent-suite/results/wzrdmail-full/COMPARISON.md`): provisioning, the draft-only key (direct send → 403), Svix verification, tier-0 threaded reply, tier-2 decision-only, tier-1 draft → decision → approve → `sendDraft`, the outbound approval round trip. Two real parity bugs were found and fixed (`createDraft` recipients from the parent; `state: "rejected"` on a 200). The block-list and calendar paths were not exercised at all (`COMPARISON.md:79-91` lists neither). The verdict there is correct: **do not cut over yet**, and the reasons below are the ones that were not written down.

### 8.4 The cutover plan

The code implies "set `MAIL_PROVIDER=wzrdmail`, redeploy". That plan strands every existing user. The plan that works:

1. **Per-row provider** (WZ-01, WZ-15, WZ-05): additive migration `agent_addresses.mail_provider text not null default 'agentmail'` (rollback = code revert; the column is harmless); `mailClientFor(provider)`; one `primaryMailbox(supabase, userId)` accessor replacing the eight lookups; `boxMailWiring()` keyed off the row; the inbound route computes the HMAC over the raw bytes against both configured secrets, records which matched, and only then parses the body (it never selects a secret from the envelope shape, which would mean branching on unverified content); deletion iterates distinct `(provider, pod_id)`. `MAIL_PROVIDER` becomes the default for *new* provisioning only, which makes the flip new-users-only by construction. Effort M.
2. **Fix what is broken for wzrdmail today, regardless of migration** (WZ-03, WZ-18): one org-scoped wzrdmail webhook created by `scripts/wzrdmail-webhook.ts`, secret into Vercel env; `ensureWebhook` becomes verify-only and fails closed before the `agent_addresses` insert. In the same change send `{ pattern }` on the wzrdmail block alias, fix the client test, and pin it with a staging test that blocks a sender and expects `message.rejected`. Effort S.
3. **Confirm the provider contract with wzrdmail** (WZ-04, WZ-06, WZ-07, WZ-11, WZ-18): `Idempotency-Key` on `/reply` and `/drafts/{id}/send` (or `client_id` on the send body), the attachment JSON field, whether unknown block-list fields are rejected or ignored, collision status, pagination filter. Pin each in an integration test against staging. Effort S, but blocks on the wzrdmail team.
4. **Approval claim-then-send** (WZ-04): `status='approving'` CAS before the send, in the single, API-route and batch paths. Effort S.
5. **Mail wiring as reconciled state** (WZ-16, WZ-19, WZ-10): split `provisionEmail` into `ensureMailbox` (provider objects and the `agent_addresses` row) and `applyMailWiring(target, userId)` (read the primary row, mint or rotate the draft-only key, install the MCP). `finishSetup` calls it on every build and replacement, next to `provisionDaytona`, and `provisionEmail` calls it on the early-return path when the box lacks the env line. Both clients return `key_id`, stored as `agent_addresses.box_key_id`, with `client_id` on create so retries replay and `deleteApiKey` on retire. Box-side changes go through one new primitive, `boxes.wiring_pending` (sealed JSON of the `.env` lines and `mcp_servers` patch), applied by `/api/cron/sweep` only when the box is `ready` with no open `agent_runs` row, instead of `systemctl restart hermes-gateway` mid-conversation. The Daytona and Composio injections and the social cutover in §9 need the same primitive; build it once. Add a `provision.test.ts` case: `switchEnvironment` → new box has the key line and the mail MCP enabled. Effort M.
6. **Migration job for existing users** (WZ-02, WZ-09, WZ-20, WZ-17, WZ-21), a separate track from the new-user flip: `POST /api/admin/mail/migrate {user_id}` + cron batch: provision the wzrdmail inbox with the same username (on collision `${username}-${first 6 of user id}`, shown to the user as "your address is …"), then swap the primary through one Postgres function (`set_primary_agent_address`) that un-retires a same-user row or inserts and retires the others in the same transaction, so A→B→A renames and a provider flip-back never leave zero primaries (WZ-20); replay `senders.blocked_at` onto the new inbox (WZ-17); re-file or dismiss pending `email_draft` decisions whose inbox is being retired, and from now on write `{ inbox_id, provider }` into `decisions.payload` so approval resolves against the inbox that holds the draft (WZ-21); retire the old row (never delete); rewrite `.env` stripping both prefixes and revoke the old key via the stored `key_id` (WZ-02, WZ-19); delete the other `mcp_servers` entry, all via step 5's `wiring_pending`. 8. **Decide calendar** (WZ-06): `hasHostedCalendar(provider)` capability flag; hide free/busy, booking and RSVP when false. Product decision whether wzrdmail will ship a calendar surface. Effort S.
9. **A parity harness that can say yes** (WZ-12, WZ-14, WZ-22): first, product pins the tier policy in `SECURITY-DECISIONS.md` (the document and `inbound.ts` currently disagree on tier 1 and tier 2); the harness asserts the pinned policy, not the current code. ### 9.4 Target design

**Decision 1, token custody: sealed columns in Supabase.** `connections.token_sealed`, `refresh_token_sealed`, `token_expires_at`, `accounts jsonb` (id/name/kind), `default_account_id`, `last_ok_at`, sealed with `lib/crypto/secretbox` under a dedicated `SOCIAL_TOKEN_KEY` with AAD bound to the row id. `secretbox` has no AAD today (the Aug "sealed secrets carry no AAD" item is still open), so this needs a `v2:` envelope format and a reseal path for existing sealed columns; scope it as its own S task. Per-tenant export (I6, "extractable with one query and one snapshot pull"): tokens sealed under a Vercel-env key are not user-exportable, which is acceptable because OAuth tokens are revocable capabilities the export re-obtains by reconnecting; say so in SECURITY-DECISIONS. This amends goal-air2 M7's "never the token, Composio holds it" and must be argued in SECURITY-DECISIONS: tokens are capability metadata, not content (C4 is about messages and memory); provider app secrets stay in Vercel env and the box holds neither (C2 unchanged); the box cannot publish with API credentials (the mirror of C10 for email), with one scoped exception: the social-engage skill's browser path with vault sign-in (`infra/template/skills/social-engage/SKILL.md:101-107,117`, propose→resume through `/api/browser/social`) remains a box-driven publish path gated by prompt policy and by a run resume the control plane cannot verify (SOC-17); the custody decision stands regardless, but the spine is single-gate only once SOC-17 lands. And the publish worker never needs a machine start to publish or poll, which is the binding limit (ARCHITECTURE §6.2). The two alternatives are rejected: a box-side vault hands the agent raw posting power and makes every publish a box start; a separate Postiz-style service adds a third data plane with plaintext tokens, a Temporal + Redis + Postgres + Elasticsearch footprint, and an AGPL network boundary.

**Decision 2, licence: cleanroom re-implementation.** Postiz is AGPL-3.0. Our reading (confirm with counsel before P1): copying provider code into `apps/web` (a proprietary control plane served over the network) triggers source-offer obligations for the combined work; running unmodified Postiz as a service confines that but brings the rejected topology. So: `lib/publish/providers/*` re-implemented in TypeScript, with Postiz used only as a behavioural spec (error-code tables, chunk sizes, the pending/finalize contract, refresh-at-expiry). Record the decision in SECURITY-DECISIONS and cite it in each provider header.

**Decision 3, the agent surface: a first-party `/api/mcp/social`** with the same gateway-token auth as the Composio proxy, exposing only `list_accounts`, `validate_draft`, `propose_post` (files a `social_post` / `content_plan` decision and returns `pending_approval`), `stage_plan` (wraps `/api/content/plan`), `post_status`, `post_metrics`. There is no raw publish tool for the agent. `content_slots.status='scheduled'` is written only by the decision-approve path, the owner-session `/api/slots`, and plan approval. Approving a `social_post` decision executes the approved payload from the control plane through the first-party provider and records `external_id` on the decision; the run resumes with the result, not with permission to post (SOC-17). Browser-only engagement actions carry the approved payload hash into the Hermes approval and the box-side guard refuses divergent text. `/api/browser/social` returns capabilities, not names (SOC-23), so a dark or text-only platform is staged and waited on, not driven through the browser. The spine becomes the single gate structurally, not by prompt.

**Decision 4, orchestration: Temporal maps onto the cron sweeper.** `scheduled → ready → publishing(phase=upload) → pending(pendingData) → publishing(phase=finalize) → published`. The 5-minute sweep (`apps/web/vercel.json:12-13`) polls `pending` rows with `checkPostStatus` (no box wake; a proposed budget of ≈ 30 min ≈ 6 sweeps), runs `finalizePost` once under the same CAS claim (`claimed_at` = heartbeat, `attempt_epoch` = idempotency witness). The platform id is checkpointed in `publish_state` before the `external_id` write and every post-claim write is epoch-guarded, so a post-publish failure finalises on resume (SOC-16). Ingest moves to package-ready time: the creative plugin reports each saved package, the control plane ingests assets and dimensions while the box is already awake and sets `package_ready_at` (SOC-21); the sweep runs every pre-flight before the first box touch (SOC-20) under a deadline budget with bounded per-user concurrency (SOC-18); publishing then never needs the box, coalescing goes to zero, and slots fire at the exact minute on `fire_at` with `scheduled_at` immutable (SOC-25). Media never passes through Vercel: the box uploads each stripped file directly to Supabase Storage through a write-only signed upload URL (SOC-19), and providers stream from Storage with Range reads: X v2 chunked, TikTok FILE_UPLOAD, YouTube resumable with the session URI in `publish_state`, pull-from-URL kept for Instagram/Facebook.

**Migration of `connections`:** `provider='air'` rows beside legacy `composio` rows (the unique key already allows both); the worker prefers an active `air` row and falls back to `composio` behind `PUBLISH_PROVIDER_<PLATFORM>`; Connect shows "Upgrade connection" per social toolkit; the first-party OAuth callback writes the `connections` row and queues a connected-tools refresh for the next natural wake instead of waking the box and restarting the gateway (SOC-26); after a user's last social toolkit moves, revoke the Composio connected accounts but keep the session for Calendar/Shopify/Gmail until those get first-party OAuth on the same sealed-token broker.

## 10. The box template, cold start, and fleet

### As built

`infra/template/setup.sh` (825 lines) bakes one Ubuntu image: Hermes at a pinned SHA in a venv outside the checkout, a prebuilt dashboard SPA (via nvm Node 24), a second Node 22 for agent-browser + Chrome for Testing, browser-use, link-cli, 1Password `op` (checksummed), Daytona (`releases/latest`), 17 hub skills + 21 local skills, OpenViking 0.4.16 in its own venv with llama-cpp compiled from source, a task router with a 1.1 GB GGUF under `~/.taskrouter`, tailscale + cotal installed-never-enabled, calendar `sync.py`, `air-learningd`, creative + air-vault plugins. Seven units start at boot; only `air-learningd` is hardened. No resident-memory or wake-time measurement exists anywhere in the repo, although three specs require one before fleet-wide rollout. No measurement exists (BOX-13), so this review states only what the component set implies: the Hermes venv and gateway, the dashboard, OpenViking with local llama-cpp embeddings, the resident task-router GGUF, agent-browser and headed Chrome cannot fit `small`, and the `default` versus `large` choice is blocked on BOX-13.

The cold resume as the platform actually behaves: the provider reports `ready` while `/home/user` is still a root-hydrated FUSE mount (~1 minute; `hermes-sidecar-owner.service:3-4`, `ARCHITECTURE.md:662`); when the real disk is swapped in, every process with a cwd or open file under it is killed, which includes `hermes-gateway`. Fleet sync waits for `HOME_STEADY`; the message path and the provisioning fork path do not. Fleet sync also resumes boxes outside the `boxes.state` machine, so a box it woke is invisible to the sweeper that would stop it (BOX-18).

### Plan

1. Fix the wake path's self-inflicted reboots (BOX-19, BOX-01 gated, BOX-04, BOX-11, BOX-21): gate the control-plane `systemctl restart` on unit state and age with a 90 s grace measured from the ready `getBox`; skip `resume` on a box already in a transitional state; `waitForHomeSteady` after a genuine resume in `ensureBoxAwake` and after `waitForBox` on the fork path; measure whether the hosted token rotates and drop the orchestrator-side `host url` from the hot loop if it does not. Gate the `ExecStartPre` mount probe on that measurement and ship it with `TimeoutStartSec=300`. Effort S. Done when a cold message issues one `resume` and no `systemctl restart` unless the unit is failed or has been active over 90 s without listening, proved by a unit test and the new phase timings.
2. Put fleet-resumed boxes inside the state machine and stop stopping from sync (BOX-18, BOX-20, BOX-02, BOX-22, BOX-10, BOX-23, BOX-25): sync writes `state` and `stop_after` around its resume and never stops a box itself; the sweeper does, and treats a NULL `stop_after` with recent `last_active_at` or an open run as busy; one box per sweep invocation; the wave moves to the end of the sweep or its own cron; `last_active_at` written with every `starting` write; every box on the channel enrolled. Without this, every rollout leaks running boxes and can kill live turns. Effort S. Done when every box the fleet resumes carries `state` and a `stop_after`, a killed sweep leaves no box running past the next tick, and a turn started mid-sync is never stopped.
3. Count starts at the source (BOX-03, BOX-13, BOX-24): `box_state_events {state:'start', source}` written inside `resume()`/`fork()` behind a widened check constraint, `start_limited` on 429, ops reading those rows; `resume_ms / ready_ms / steady_ms / health_ms` recorded per wake; the fork size passed explicitly and vcpu/memory persisted so sizing can be audited. Every sizing, lazy-activation and hydration-gate decision in this section is blocked on these numbers. Effort S-M. Done when the ops page reports starts per hour from `resume()`/`fork()` calls and 429s, not from run rows, and every wake records its four phase timings.
4. Make sync cheap and honest (BOX-05, BOX-06, BOX-16): prebuilt llama-cpp wheel as a separate checksummed R2 object referenced by `template_releases` and installed with `--find-links`; guard every heavy step; split the sync into bounded commands; `verify-box.sh` checks openviking/learningd/`ovctl status`; `restart --no-block` for the oneshot. Effort M. Done when a no-change sync of one box finishes inside its command budget with no compilation, and `verify-box.sh` fails when OpenViking or the learning daemon is unhealthy.
5. Pin everything and lock the venv (BOX-07, BOX-17): versioned uv/agent-browser/daytona with sha256; GGUF by commit revision + hash; `hermes-requirements.lock` with hashes; one `HERMES_REF` file; a CI grep that fails on `latest`, `resolve/main`, `curl | sh`. Effort M. Done when a CI grep fails on `latest`, `resolve/main` or a piped installer anywhere under `infra/`, and two builds of the same template commit install identical versions.
6. Trim the resident set (BOX-08, BOX-12, BOX-15): one end state for the task router, used everywhere in this document: the service ships disabled now, and the unit and the GGUF leave the template in the next release, so neither costs snapshot or hydration time; its deterministic heuristics are kept as a pure function in the control plane where §7.5 uses them for the task ledger. `OOMScoreAdjust` and `Nice` on the loopback services now, `MemoryMax` once BOX-13's RSS numbers exist, and no address filter on `openviking.service` (it calls the inference gateway); drop nvm by building the SPA off-box; purge the C++ toolchain after the wheel is built. Effort S. Done when a freshly forked box shows no task-router unit, no GGUF under `$HOME`, and a measured idle resident set recorded in `docs/reports`.
